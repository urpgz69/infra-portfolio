# Ai-Myaong (AIみゃおん) — インフラ・デプロイ担当 概要

## プロジェクト概要
ペットの見守りを目的とした IoT プラットフォーム。カメラ映像から **YOLO による物体検出**を行い、留守中の人物検知・活動量の記録・遠隔給餌を提供する。Web アプリケーションと、ローカルの推論処理・ハードウェア群を連携させる構成が求められた。

- **リポジトリ:** https://github.com/xorb811-ship-it/Ai-Myaong_IoT_project （ブランチ: `deployfinal`）
- **技術スタック:** FastAPI / React (Vite) / YOLO・OpenCV / Oracle Cloud ATP / Docker (マルチステージ) / Railway / Cloudflare Tunnel / MQTT (HiveMQ) / Raspberry Pi・ESP32

## 担当範囲（関与の度合いで区分）
- **主導（自ら調査・設計・構築）:** Railway へのデプロイ構成全般、マルチステージ Dockerfile によるフロントエンド同梱ビルド、ビルド時変数と実行時変数の分離設計、Oracle ATP のウォレット注入、Cloudflare Tunnel による映像配信経路の構築
- **調整のみ（主担当ではない）:** 映像推論ワーカー (`vision_to_frontend.py`) のアプリケーションコード。デモ時のフレームドロップについて原因箇所を特定し、根拠とともに担当者へ引き継いだ（実装変更は担当外）
- **チーム協議のうえ反映:** 推論処理の実行場所（Raspberry Pi → デスクトップ）、映像配信をバックエンド経由にしない方針

## インフラ構成
```
[ローカル]                    [Cloudflare Tunnel]      [Railway（単一サービス）]
 MJPEG サーバ ──────────────► https://<tunnel>          ┌────────────────────┐
      │                            │                    │ FastAPI (uvicorn)  │
      ▼                            │                    │ + frontend/dist    │
 OpenCV ワーカー                    │                    └────────────────────┘
  ・YOLO 推論                       │      検出座標 (JSON)      ▲        │
  ・検出座標のみ送信 ────────────────┼──────────────────────────┘        │
                                   ▼                                   ▼
                              [ブラウザ]                          Oracle ATP
                            映像 ＋ 検出枠オーバーレイ              (Wallet / TLS)
```
フロントエンドのビルド成果物をバックエンドのイメージに同梱し、FastAPI から静的配信する構成とした。これによりフロントエンドと API が**同一オリジン**となり、CORS 設定と公開サービス数の両方を削減している。

## 主な成果① ― 演算とホスティングの分離
YOLO 推論は CPU を継続的に占有するワークロードであり、コンテナ稼働時間で課金される PaaS の料金モデルとは相性が悪い。一方、API と静的配信は待機型であり PaaS に適している。そこで **演算はローカル、状態管理とホスティングはクラウド**に分離し、両者の間は検出座標（軽量な JSON）のみをやり取りする構成とした。

さらに、映像そのものはバックエンドを経由させず、トンネル経由でブラウザへ直接配信する経路とした。MJPEG はフレームごとに完全な JPEG を送るため帯域消費が大きく、クラウドを中継させると帯域コストと遅延の双方が増加するためである。

結果として、**映像の経路と検出結果の経路が独立**する構成となった。これは設計上の副次効果として、障害の切り分けを容易にした（後述）。

## 主な成果② ― ビルド時設定と実行時設定の境界を定める
Vite はクライアント側の設定値をビルド成果物に埋め込む仕様のため、`VITE_*` 変数の変更には再ビルドを要する。一方、Railway のサービス変数は再起動のみで反映される。

本構成で最も変更頻度が高い値は**映像ストリーム URL** であった。一時トンネルは起動のたびに URL が変わるためである。しかしフロントエンドの実装を確認したところ、`VITE_STREAM_URL`（ビルド時）が設定されている場合、バックエンドが実行時に URL を返す `/api/stream/url` は呼び出されない構造になっていた。

つまり動作はしていたが、**URL が変わるたびに再ビルドが必要な状態に固定されていた**。加えて既定値がアプリ自身のルート URL であったため、変数の設定漏れ時には「エラーを出さずに映像だけ表示されない」形で失敗する設計上のリスクもあった。

ここから、**変更頻度が高い値ほど実行時設定に寄せるほど変更コストが下がる**という判断基準を得た。改善方針として、ビルド時変数を未設定にして実行時エンドポイントへフォールバックさせる構成を整理している。

## その他の要点
- **ウォレットの注入:** Railway のファイルシステムは再デプロイで初期化されるため、Oracle ATP のウォレットは base64 化した環境変数として保持し、起動時に展開する方式とした（「ホストにある ≠ 実行環境にある」への対応）
- **HTTPS 混在の回避:** ローカルの HTTP 映像を HTTPS ページから読み込むと mixed content でブロックされるため、Cloudflare Tunnel で HTTPS 化して配信経路を成立させた
- **ログの読み分け:** トンネルの `stream canceled ... error code 0` は HTTP/2 の `NO_ERROR` であり、クライアント側の正常終了を示す。障害ではないが、**頻度が高い場合は再接続の多発を意味する**ため、異常の有無ではなく発生頻度を指標として扱った

## 学んだこと
- **設定値は「変更コストがどこに蓄積するか」で配置を決める** ― 動作している構成でも、変更頻度と反映コストが噛み合っていなければ運用上の負債になる
- **経路を分ければ障害も切り分けられる** ― 「映像は正常だが検出枠だけ止まる」のように、構成の分離がそのまま診断の手がかりになる。設計は可用性だけでなく診断可能性も決める
- **エラーらしさと実際の異常を切り離して読む** ― ログの見た目ではなく、プロトコル上の意味と発生頻度で判断する
- **担当の境界を守りつつ、原因は特定して引き継ぐ** ― 担当外の領域でも、症状の切り分けと根拠の提示までを行うことで、チームとしての解決速度は上がる
