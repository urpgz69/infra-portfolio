# PaaS 배포 & 하이브리드(로컬 추론) 구성 정리

> 인프라 배포 참고 노트. Ai-Myaong (Railway + 로컬 YOLO) 경험 기반.
> 기존 노트(EC2 + Docker Compose + Apache)와 대비되는 **PaaS 배포** 관점 정리.

---

## 1. 핵심 개념 구분

기존 배포(EC2 / Azure VM)와 PaaS(Railway / Render)는 **관리 경계가 다르다.**

| 구분 | 직접 서버 (EC2, VM) | PaaS (Railway) |
| --- | --- | --- |
| 실행 단위 | 내가 띄운 컨테이너 | 플랫폼이 관리하는 컨테이너 |
| 배포 방식 | 이미지 push → SSH → `docker compose up` | git push → 플랫폼이 빌드·기동 |
| 리버스 프록시 | 직접 구성 (Nginx / Apache) | 플랫폼이 라우팅·TLS 처리 |
| TLS 인증서 | Let's Encrypt 직접 갱신 | 자동 |
| 파일시스템 | 영속 (EBS 등) | **재배포 시 초기화** |
| 비용 | 인스턴스 시간 | CPU·메모리·트래픽 사용량 |

**핵심 감각:** PaaS는 "서버를 안 만지는 대신, 플랫폼 규칙 안에서만 움직인다."
Nginx 설정·인증서 갱신 같은 작업이 사라지는 대신, **파일 영속성과 설정 주입 방식**에 제약이 생긴다.

### Railway의 슬립(Serverless)은 기본값이 아니다

- Railway는 기본적으로 **상시 컨테이너**로 동작한다 → 콜드스타트 없음
- `Settings → Deploy → Serverless`를 **켰을 때만** 슬립한다
- 슬립 판정 기준은 **아웃바운드 트래픽 10분 무발생** (인바운드는 판정에 안 들어감)
- 즉 외부에서 요청이 들어와도 그것만으로는 안 깨어 있고, DB 커넥션 같은 아웃바운드가 있으면 계속 깨어 있음

> "PaaS = 콜드스타트"라고 뭉뚱그리지 말 것. 서버리스 함수(Lambda/Vercel)와 컨테이너 PaaS는 다르다.

## 2. 워크로드를 어디에 둘 것인가

무거운 연산을 클라우드에 올릴지 판단하는 기준.

| 워크로드 성격 | 예시 | 적합한 위치 |
| --- | --- | --- |
| **상시 점유형** (CPU/GPU 계속 사용) | YOLO 추론, 인코딩 | 로컬 / 전용 인스턴스 |
| **대기형** (요청 있을 때만) | REST API, 정적 서빙 | PaaS |
| **버스트형** (가끔 무겁게) | 배치, 리포트 생성 | 서버리스 / 잡 큐 |

**판단 근거:** PaaS는 컨테이너 가동 시간 + 사용량으로 과금한다.
추론처럼 CPU를 계속 100% 쓰는 워크로드는 과금 모델과 정면으로 안 맞는다.

**분리 설계 시 원칙:** 무거운 쪽과 가벼운 쪽 사이에는 **가장 가벼운 데이터만** 흐르게 한다.

```
[나쁨] 로컬에서 추론 → 박스 그린 영상을 클라우드로 업로드 → 브라우저
        = 영상이 클라우드를 왕복 (대역폭·지연 폭증)

[좋음] 로컬에서 추론 → 좌표 JSON만 클라우드로 POST
        영상은 별도 경로로 브라우저에 직접 전달
        브라우저가 영상 위에 좌표를 오버레이
```

## 3. 빌드타임 설정 vs 런타임 설정 (가장 중요)

**두 프로젝트에서 연속으로 밟은 함정.** 패턴으로 외워둘 것.

### 3-1. 왜 생기는가

Vite 같은 프론트 빌드 도구는 `VITE_*` 환경변수를 **번들 코드에 문자열로 박아버린다.**
따라서 값을 바꾸려면 재빌드가 필요하다. 반면 백엔드 환경변수는 재시작만으로 반영된다.

| 구분 | 반영 방법 | 소요 |
| --- | --- | --- |
| 빌드타임 (`ARG` → `VITE_*`) | 재빌드 + 재배포 | 수 분 (`npm ci`부터) |
| 런타임 (서비스 변수) | 재시작 | 수십 초 |

### 3-2. 반복된 실패 사례

| 프로젝트 | 증상 | 원인 |
| --- | --- | --- |
| VR-Curator | HTTPS 페이지에서 WebSocket 차단 (Mixed Content) | `ARG VITE_WS_BASE_URL=ws://...` 기본값이 박힘 |
| Ai-Myaong | 스트림 주소 변경 시마다 재빌드 필요 | `VITE_STREAM_URL`이 런타임 엔드포인트를 단락시킴 |

두 경우 모두 **"동작은 했다."** 문제는 동작 여부가 아니라 **변경 비용이 어디에 쌓였는가**였다.

### 3-3. 단락(short-circuit) 구조에 주의

```js
// 빌드타임 값이 있으면 런타임 엔드포인트를 아예 호출하지 않는다
if (STREAM_URL) {
  return { url: resolveStreamUrl(STREAM_URL), mode: "external" };
}
const data = await request("/api/stream/url");   // ← 위에서 return되면 도달 불가
```

서버가 런타임에 값을 내려주는 엔드포인트를 만들어놔도, **프론트가 빌드타임 값을 우선하면 무용지물**이 된다.

### 3-4. 원칙

1. **변경 빈도가 높은 값일수록 런타임으로 내린다** (서버가 API로 내려주게)
2. **`ARG` 기본값은 비워둔다** — 기본값이 있으면 "설정 누락"이 조용한 오동작이 된다
3. 절대 URL을 굳히지 말고 **현재 origin 기준으로 파생**시킨다
4. 빌드 산출물을 검사한다

```bash
# 번들에 환경별 절대 URL이 박혔는지 확인
grep -R "localhost\|127.0.0.1\|ws://\|:8080" frontend/dist
```

### 3-5. Railway에서 빌드타임 변수 주입

Dockerfile에 `ARG`로 **선언해야만** 빌드 시점에 주입된다. 선언 안 하면 그냥 무시된다.

```dockerfile
FROM node:20-alpine AS frontend-build
ARG VITE_API_BASE_URL          # ← 선언 필수
ENV VITE_API_BASE_URL=$VITE_API_BASE_URL
RUN npm run build
```

- **주의:** `ARG`는 **스테이지마다** 다시 선언해야 한다 (멀티스테이지에서 자주 빠뜨림)
- sealed variable(시크릿)도 빌드·배포 양쪽에 값이 제공된다. 단 UI/API로 되읽기는 불가
- **`ARG`로 넘긴 값은 이미지 히스토리에 남는다** → 진짜 시크릿은 런타임 ENV로

## 4. 단일 서비스로 묶기

프론트 빌드 산출물을 백엔드 이미지에 넣고 백엔드가 정적 서빙하는 구성.

```dockerfile
# 1단계: 프론트 빌드
FROM node:20-alpine AS frontend-build
...
RUN npm run build

# 2단계: 백엔드 + 프론트 산출물 동봉
FROM python:3.11-slim
ENV FRONTEND_DIST_DIR=/app/frontend/dist
COPY backend /app/backend
COPY --from=frontend-build /app/dist /app/frontend/dist
```

| | 분리 배포 | 단일 서비스 |
| --- | --- | --- |
| CORS | 설정 필요 | **불필요 (동일 오리진)** |
| API 주소 | 명시 필요 | `window.location.origin`으로 충분 |
| 배포 단위 | 독립 (프론트만 재배포 가능) | 항상 함께 |
| 장애점 | 2개 | 1개 |

**판단 기준:** 데모·소규모에서는 **구성 요소를 줄이는 것 자체가 안정성**이다.
프론트를 자주 독립 배포해야 하는 규모가 되면 그때 분리한다.

## 5. 스트리밍 경로 설계 (MJPEG)

### 5-1. Mixed Content 제약

HTTPS 페이지에서는 `http://` 리소스를 브라우저가 차단한다.
로컬 카메라 서버는 보통 HTTP라, **HTTPS로 노출시키는 수단이 반드시 필요**하다.

```
[차단됨] https://app.example.com  →  http://localhost:8081/stream.mjpg
[가능]   https://app.example.com  →  https://<tunnel>.trycloudflare.com/stream.mjpg
```

> VR-Curator의 `ws://` 차단과 완전히 같은 원리다. **HTTPS 페이지는 하위 리소스도 전부 보안 연결이어야 한다.**

### 5-2. 터널 선택

| 종류 | 주소 | 용도 |
| --- | --- | --- |
| quick tunnel (`--url`) | **실행마다 랜덤 변경** | 임시 테스트 |
| named tunnel (설정 기반) | 고정 | 시연·운영 |

quick tunnel 주소를 빌드타임 변수에 넣으면, 터널 재시작 = 재빌드가 된다 (3장과 연결).

### 5-3. 대역폭

MJPEG는 프레임마다 완전한 JPEG를 보내므로 대역 소모가 크다.

- 소비자가 늘면 그만큼 배수로 나간다 → **브라우저와 워커가 같은 터널을 동시에 빨지 않게** 한다
  (워커는 로컬 IP로 직결, 터널은 브라우저 전용)
- 소스에서 해상도·fps·JPEG 품질을 낮추는 것이 가장 효과가 크다 (예: 640×360 / 10fps / 품질 60)

## 6. 문제와 해결

### 6-1. 영상은 나오는데 검출 박스만 끊김

**증상:** 브라우저에 영상은 매끄럽게 재생되나 오버레이 박스가 떴다 사라졌다 반복.

**원인:** 워커가 **매 프레임 YOLO 추론 + 동기 POST**를 수행. POST 타임아웃이 코드에 `0.5`초로 하드코딩되어 있어, 공인망(TLS 핸드셰이크 포함)에서 초과 시 **메인 루프 전체가 최대 0.5초씩 정지**했다. 프론트는 검출 결과가 오래되면(freshness 게이팅) 박스를 아예 안 그린다.

```python
requests.post(f"{backend_url}/api/vision/detections", json=payload, timeout=0.5)
requests.get(f"{backend_url}/api/vision/control", timeout=0.5)
```

**해결 방향:**

| 조치 | 효과 |
| --- | --- |
| N프레임마다만 추론 | 추론 부하 1/N |
| 추론 입력 축소 (640 → 416) | 연산량 절반 이하 |
| POST 스로틀 (10Hz) + 스레드 분리 | 네트워크가 캡처 루프를 막지 않음 |
| 타임아웃 0.5 → 2~3초 | 지연 응답 시 루프 정지 방지 |

**재발 방지:** **네트워크 호출을 실시간 루프 안에서 동기로 돌리지 않는다.**
로컬 개발에서는 응답이 1ms라 안 드러나고, 공인망에 올린 순간 터진다.

### 6-2. 터널 로그에 에러가 계속 찍힘

**증상:**

```text
ERR error="stream 17 canceled by remote with error code 0" originService=http://127.0.0.1:8081
```

**원인:** 이건 **에러가 아니다.** HTTP/2에서 `error code 0` = `NO_ERROR`, 즉 클라이언트가 스트림을 **정상 종료**했다는 뜻. MJPEG는 계속 열려 있는 롱 스트림이라, 소비자가 끊고 재접속할 때마다 한 줄씩 남는다.

**해결:** 로그 자체는 무시. 단 **빈도**는 지표로 삼는다 — 잦으면 재접속이 반복된다는 뜻이고 이는 프레임 드랍과 직결된다.

**원인 절개:**

```
워커를 끈다
  → 로그가 계속 나온다  = 브라우저 쪽 (img 리마운트, 재요청)
  → 로그가 멈춘다       = 워커 쪽 (스트림을 못 따라가 재접속 반복)
```

**재발 방지:** 로그는 **"에러처럼 보이는가"가 아니라 "프로토콜상 무슨 의미인가"**로 읽는다.
`ERR` 레벨로 찍혔다고 전부 장애가 아니다.

### 6-3. 처음에만 느리고 조금 기다리면 정상

**증상:** 기동 직후 프레임 드랍이 심하다가 수십 초 뒤 안정화.

**원인:** 성격이 다른 워밍업이 **여러 개 겹쳐 있다.** 하나로 뭉뚱그리면 진단이 안 된다.

| 요인 | 발생 조건 | 재발성 | 대응 |
| --- | --- | --- | --- |
| YOLO/PyTorch 초기 추론 | 워커 기동 시 | 1회 | 더미 프레임으로 사전 예열 |
| Railway 슬립 | Serverless 토글 ON일 때만 | 반복 | 토글 OFF |
| Oracle ATP 커넥션 / auto-stop | 장기 미사용 후 | 반복 | 사전 기동 확인 |
| 터널·브라우저 버퍼링 | 스트림 최초 연결 | 1회 | 미리 틀어두기 |

**해결:** 가장 흔한 범인은 **모델 워밍업**이다. 루프 진입 전에 예열한다.

```python
import numpy as np
warm = np.zeros((480, 640, 3), dtype=np.uint8)
for _ in range(3):
    model(warm, verbose=False)
```

**재발 방지:** "콜드스타트"를 한 덩어리로 보지 말고 **계층별로 분리**한다.
1회성인지 반복성인지를 구분해야 시연 대비가 가능하다.

### 6-4. 런타임 설정이 반영되지 않음

**증상:** 백엔드 환경변수(`CAMERA_STREAM_URL`)를 바꿔도 프론트 동작이 그대로.

**원인:** 프론트가 빌드타임 값(`VITE_STREAM_URL`)을 우선해 런타임 엔드포인트를 호출하지 않음 (3-3 참조).

**해결:** 빌드타임 변수를 비우고 런타임 엔드포인트로 폴백시킨다.

**재발 방지:** "환경변수를 바꿨는데 안 먹는다" → **그 값이 빌드타임인지 런타임인지부터 확인**한다.
빌드타임 값은 이미 번들에 박혀 있으므로 재배포로도 안 바뀐다(재빌드여야 함).

## 7. 자주 밟는 함정

- **PaaS의 파일시스템은 휘발성** — 재배포하면 초기화된다. 지갑·인증서는 파일로 두지 말고 **base64 환경변수로 주입 후 기동 시 전개**
  (기존 노트의 "호스트에 있다 ≠ 컨테이너에서 보인다"의 PaaS 버전)
- **`ARG`를 스테이지마다 재선언 안 함** — 멀티스테이지에서 값이 조용히 빈 문자열이 된다
- **`ARG` 기본값에 실제 값을 박아둠** — 설정 누락이 에러 대신 오동작으로 나타난다. 심지어 그 기본값이 리포에 커밋된다
- **로컬에서 안 드러나는 타임아웃** — 루프 안의 동기 네트워크 호출은 로컬(1ms)과 공인망(수백 ms)에서 완전히 다르게 동작한다
- **같은 기기에서 무거운 연산 + 시연 브라우저** — 자원 경합으로 영상까지 버벅인다. 기기를 나눈다
- **임시 터널 주소를 고정 설정에 넣음** — 재시작하면 주소가 바뀐다
- **클라이언트 키를 Dockerfile에 하드코딩** — Vite 변수는 어차피 번들에 노출되지만, 커밋하면 git 히스토리에 남는다. EmailJS 등은 **도메인 제한**을 반드시 건다

## 8. 배포 전 체크리스트

### 설정

- [ ] `VITE_*` 값이 코드 / Dockerfile / 플랫폼 변수 **세 곳에서 이름이 정확히 일치**하나
- [ ] `ARG`가 필요한 스테이지마다 선언돼 있나
- [ ] `ARG` 기본값에 환경별 절대 URL이 박혀 있지 않나
- [ ] 자주 바뀌는 값이 빌드타임에 있지 않나
- [ ] 빌드 산출물에 `localhost` / `http://` / 내부 포트가 없나 (`grep -R ... dist`)

### 플랫폼

- [ ] Serverless(슬립) 토글 상태 확인
- [ ] 파일시스템 휘발성 전제로 시크릿·인증서 주입 방식이 잡혀 있나
- [ ] 외부 DB(ACL)에 배포 서버에서 접속 되나
- [ ] DB 인스턴스가 기동 상태인가 (자동 정지 여부)

### 연결

- [ ] HTTPS 페이지에서 불러오는 리소스가 전부 HTTPS/WSS인가
- [ ] 터널이 필요한 경우 주소가 고정인가, 변경 시 반영 경로가 재빌드가 아닌가

### 시연 직전

- [ ] 무거운 연산 프로세스를 **미리 기동**해 예열 완료
- [ ] 스트림을 미리 연결해 버퍼 안정화
- [ ] 워커·서버 로그에 반복 에러 없나
- [ ] 연산 기기와 시연 기기가 분리돼 있나

## 9. 다음 배포에서 지킬 원칙

1. **설정값은 "변경 빈도"로 배치를 결정한다.** 자주 바뀌면 런타임, 거의 안 바뀌면 빌드타임.
2. **`ARG` 기본값은 비운다.** 누락이 에러로 드러나야지, 조용한 오동작이 되면 안 된다.
3. **실시간 루프 안에 동기 네트워크 호출을 두지 않는다.** 두더라도 타임아웃을 로컬 기준으로 잡지 않는다.
4. **경로를 분리해두면 장애도 분리된다.** 어디가 깨졌는지 증상만으로 좁힐 수 있게 설계한다.
5. **로그는 레벨이 아니라 의미로 읽는다.** `ERR`도 정상일 수 있고, 정상 로그도 빈도가 지표가 된다.
6. **"동작한다"에서 검증을 멈추지 않는다.** 동작 여부와 변경 비용·실패 모드는 별개 문제다.
